## Smallest reproducer + regression tests (Oct 30, branch `minimize-counterexample` on origin/main b5b32e0, merged to origin/main and deployed with the engine at 1df23cf (Oct 30); contract minimal-reproducer v0.1, run v0.18)
- **What:** when the Java differs from the COBOL, the failing input is cut down with NO model call: ddmin over the input records (1-minimal when it completes), then field-level simplification (each field to 0 / a smaller number / spaces / fewer characters, byte length preserved, REDEFINES views included, kept only if the same discrepancy remains). The oracle is the differential harness (build once, run both, `diff.compare` + exit code + stdout). "Same discrepancy" = same kind and same differing output fields; `--strict` also pins the differing values (without it a smaller input can drift to another manifestation: CHQCLR's `20.00 vs 0.00` became spaces vs `00000`).
- **Where:** `services/verifier/diocle_verifier/minimize.py` (new; mutate.py untouched). CLI `python -m diocle_verifier minimize RUN_DIR --case ID [--java-dir D] [--from-report] [--strict] [--max-runs 150] [--max-seconds 120]`; `python -m diocle_verifier replay CASE_DIR|RUN_DIR --java-dir D`. Saves `RUN_DIR/reproducers/<id>.json` and `RUN_DIR/regression/<id>/{case.json,input.dat,expected-output.dat,expected-stdout.txt}` (expected bytes written by GnuCOBOL; replay needs only a JDK).
- **Repair loop:** `run --minimize` (converter, opt-in, caps `MINIMIZE_MAX_RUNS/SECONDS/CASES` = 150 / 120 s / 3 per run, no model cost). Breaker counterexamples and failed held-out certifications are reduced against the pre-fix Java; the repair agent's note carries the reduced input, the fields that matter and the first differing bytes instead of a raw record or batch. After the repair every saved regression case is replayed; a failure revokes certification. Skipped when `DIOCLE_SANDBOX_URL` is set (it builds locally; no sandbox job yet).
- **API/web:** `GET /runs/{id}/reproducers`, `GET /runs/{id}/reproducers/{case}/regression` (read-only; visitor runs withheld); "Smallest reproducer" card in `runs-view.tsx` (shown when the run has a breaker break or `reproducers`). ## Mutation testing: how strong is the verification? (Oct 30, branch `mutation-testing` on origin/main b5b32e0, merged to origin/main and deployed with the engine at 1df23cf (Oct 30); contract mutation-report v0.1, additive)
- **What:** `python -m diocle_verifier mutate RUN_DIR [--max-mutants 40] [--max-extra 60] [--seed S]` seeds deterministic source-level faults into a COPY of a certified run's Java (`diocle_verifier/mutate.py`), compiles each, and compares it with the GnuCOBOL original on the run's certification-seed inputs (compare, exit code, stdout). Survivors are re-run on a shared pool of extra inputs (boundary neighbours, field pairs at extremes, duplicated and blank keys; no model). Writes `mutation-report.json`; API `POST/GET /runs/{id}/mutation` (same lock as re-verify, certified non-visitor runs only, 60 s pause between jobs, 502 when the verifier fails, never a made-up report); sandbox job kind `mutation` (600 s, clamped caps); card on the run page.
- **Follow-ups (reviewer):** timeouts retried once and shown as "of which N timed out", `baselineSeconds` and `inputs.seedSource` (certification | default) in the report, cooldown set in a finally, card polls GET after a failed POST (the POST is synchronous), augmentation build failures recorded as not run.
- **Honest labels:** a survivor is a coverage question, not a defect; the score is not a confidence score; equivalent-suspected means identical javap bytecode only; timeouts count as detected. Single-input/single-output programs only (others: status `unsupported`). Extra inputs vary only the base layout (CHQCLR's record is a type byte plus an opaque body, so only 6 extras were possible). No coverage tool, so mutants in unreachable code (for example the line-sequential fallback reader in generated Java) survive.
- **Real numbers (local Mac, GnuCOBOL 3.2, JDK 21, 40 mutants, seed 1026, ~27 s each):** `CHQCLR` (1004 inputs): 9 killed, 30 survived, 1 not compiled, 0 suspected equivalent, score 0.231; 6 extra inputs killed 1 of 30 survivors; `LOANAMRT` (1021 inputs): 25 killed, 14 survived, 1 not compiled, 0 suspected equivalent, score 0.641; 80 extra inputs killed 0 of 14 survivors; `FXCONV` (1016 inputs): 25 killed, 13 survived, 2 not compiled, 0 suspected equivalent, score 0.658; 46 extra inputs killed 0 of 13 survivors.

- **What:** a bundled spoken question -> Muse Voice Transcribe -> Muse Spark proposes 1-3 claims (documenter format, question-focused prompt) -> the original COBOL runs on the examples (GnuCOBOL, sandbox on the public path) -> verdicts -> an answer assembled by a fixed template from CONFIRMED claims only. - **Route discovery (the key fact):** `muse-voice-transcribe-1.0` is NOT on `/v1/chat/completions`, `/v1/responses` or `/audio/transcriptions` (404). Found by reading the Muse Code binary's strings and watching what `muse voice transcribe` sends to a local WebSocket listener (`TBH_VOICE_ASR_ENDPOINT` override; no HTTP probes against Meta were needed): a duplex **WebSocket `wss://shortwave.facebook.com/voyager/v1/asr/duplex`**. The same Meta key works (no separate credential). Accepted audio: raw PCM 16 kHz mono (Muse Code also takes m4a/wav and converts); we accept only 16 kHz mono 16-bit WAV, validated by bytes, <= 10 s and <= 500 KB. Limits of the service itself were not found (Muse Code has a clip-length cap; its value is not in the strings we read). **This is Meta's client protocol, an undocumented internal-looking host, not a public API: it may change or be closed to third parties.** The product does not depend on the Muse Code binary.

- **Engine redeploy checklist (not done):** amd64 image build; `docker compose exec sandbox cobc --info | grep indexed` shows BDB; `/verify` on `samples/vsam-customer-update` passes; `samples/vsam-alternate-key` is refused; DB2 sample and CHQCLR still green; sandbox tmpfs and fsize limits adequate for BDB files.
- **What:** programs with ORGANIZATION INDEXED files in the stated subset `ksds-subset-1` are no longer refused. The claim is exactly: *equivalent on GnuCOBOL's INDEXED file handler (Berkeley DB), for this subset of operations, on the inputs tried.* Never "VSAM-verified". Subset (single definition: `services/analyzer/diocle_analyzer/keyed.py`, listed in the README and `services/verifier/README.md`): one RECORD KEY (elementary alphanumeric or unsigned DISPLAY numeric), ACCESS SEQUENTIAL/RANDOM/DYNAMIC, FILE STATUS required, OPEN INPUT/OUTPUT/I-O (one mode per file), READ, READ NEXT, WRITE, REWRITE, DELETE, START (=, >=, >, NOT <), CLOSE. Refused with the exact reason: alternate keys, WITH DUPLICATES, RELATIVE, LOCK MODE / WITH LOCK, READ PREVIOUS, START < / <=, OPEN EXTEND, several OPEN modes, group/signed/packed/binary keys, no FILE STATUS, DECLARATIVES, keyed files with EXEC SQL.
- **Spike results (step 0):** (a) the Homebrew cobc has `indexed file handler : BDB`; INDEXED programs compile with `-std=ibm` and run. **Collating sequence:** GnuCOBOL's indexed handler orders keys by RAW BYTES and ignores `-fdefault-colseq=EBCDIC` (checked on START and READ NEXT with keys ` 001`, `1001`, `A001`, `B002`, `b001`; the 40-sequence fuzz test also passes under that flag). So the Java must compare keys as unsigned bytes, not EBCDIC; the translator prompt says so. (b) The engine image built GnuCOBOL `--without-db`: keyed files cannot run there. Fix, already in `deploy/Dockerfile.api`: `libdb-dev` + `--with-db` in the build stage, `libdb5.3t64` (1.7 MB installed) in the final stage; no other change. Built locally (arm64, `docker build -f deploy/Dockerfile.api -t diocle-engine:vsamtest .`): `cobc --info` shows BDB, `libcob.so` links `libdb-5.3.so`. A container with the production sandbox flags (read-only rootfs, tmpfs /tmp exec 384m, cap_drop ALL + SETUID/SETGID/KILL, no-new-privileges, pids 256, 768m, 1 cpu, fsize 256 MB) compiled and ran a keyed program as root and as uid 65534, and its HTTP sandbox verified `samples/vsam-customer-update` PASS 114/114 from the host (`DIOCLE_SANDBOX_URL=http://127.0.0.1:18100`); a Java missing its REWRITE was caught by the keyed-file diff (first mismatch key and records shown); a Java that reads `DD_CUSTMAST` itself was refused before it ran. Not covered: the amd64 server build (the Mac is arm64); the BDB file is 8 KB for 4 records, so a large keyed file is bounded by the 16 MB read cap and the sandbox ulimit. (c) Decision: verifier-owned `dbsupport/DioKsds.java` (like DioSql) with an in-memory sorted map, saved as plain fixed-length records in key order at CLOSE and at JVM exit (the implicit close at STOP RUN); the original runs on the real handler in its own directory.
- **Design decisions:** the Java runs FIRST in its own directory on its own copy of the seeds, then the loader/dumper COBOL programs (generated by `ksds.py` from the layout, compiled with cobc) build the original's file and read it back, so no Python code parses Berkeley DB; inputs, seeds, COBOL source, modules, copybooks are hashed around the Java run (any change fails closed), stray `original`/`*.kf`/`ksds-tools` fail closed, the Java is statically refused if it names a keyed DD in `getenv`, a `.kf`/`kseed` path, or uses reflection/processes/native/net; a keyed program whose files equal their seeds on both sides is not certified. Seed keys: boundary keys (all spaces, 0, 9, A, Z, a, z), random keys with leading characters that order differently in ASCII and EBCDIC; transaction fields linked by name and width (`sample.json` `ksds.keyLinks`, written by the analyzer) draw about 50% seeded keys and 40% absent keys. The analyzer computes the key offset; the verifier recomputes it from the layout and fails closed if they differ. DioKsds quirks found by experiment on the real handler and reproduced: the first READ NEXT returns the record that was first when the file was opened (a record written before it, with a smaller key, is skipped), a failed START (23) makes the next READ NEXT report 46, WRITE and a failed READ by key do not move the position, a sequential REWRITE/DELETE needs the immediately preceding successful READ (43 otherwise), WRITE on a sequential-access file opened I-O is 48, REWRITE of an absent key in random/dynamic access is 21 (not 23).
